# Школьные аккаунты

Сайт остаётся на GitHub Pages. Аккаунты, домашка и результаты обслуживает функция `school-api` проекта Supabase `literature-school`.

## Интерфейс

- Учитель: вход по паролю, свободные игры, вопросы и ответы, назначение домашки, просмотр результатов.
- Ученик: фамилия, имя, класс 7А–9Б, собственный пароль от 6 символов. Не более 15 регистраций на класс.
- Управление учениками доступно только владельцу: изменение данных, назначение нового пароля, удаление, сброс попыток конкретного задания, исправление процента завершённой попытки. Все административные изменения записываются в `school.audit`.
- Удаление ученика удаляет его результаты и сеансы. Сброс попыток удаляет результаты выбранного задания. Интерфейс запрашивает подтверждение.

## Результаты

Сервер выдаёт вопросы и броски, проверяет ответы и сохраняет каждое действие. Нельзя отправить собственный процент вместо ответов. Повторный запрос с уже обработанной ревизией не меняет результат. Незавершённая попытка возобновляется; выход не возвращает лимит.

Правда/ложь: правильные ответы / 10. Бродилка: правильные / все ответы. Кроссворд: разгаданные слова / (количество слов + все ошибки). Каждая проверка неверного неразгаданного слова добавляет ошибку; разгаданные слова закрепляются. Досрочное завершение по кнопке «Завершить» даёт 0%.

В итог входят лучшие завершённые попытки по назначенным заданиям текущего класса. Эксперт исключён. Невыполненное задание считается за 0%. Веса категорий: бродилки 50%, кроссворды 30%, правда/ложь 20%; при отсутствии категории веса нормализуются. Закрытие доступа не стирает результаты. Оценки: 85% → 5, 70% → 4, 55% → 3, 40% → 2, 25% → 1, ниже → 0. Повторное назначение меняет общий лимит, не создаёт новую домашку и не сбрасывает попытки.

## Технические границы

- Пароли не хранятся открыто: PBKDF2 SHA-256, 210000 итераций, отдельная случайная соль. Просмотр паролей не реализован; используется сброс.
- 12-часовые сеансы: случайный токен в sessionStorage, в базе только SHA-256 токена. Роль берётся из базы на каждом запросе, не из браузера.
- `school` не является публичной схемой API; RLS включён, разрешающих политик для клиентов нет. Сообщение анализатора «RLS Enabled No Policy» в данном случае означает намеренный запрет прямого клиентского доступа.
- Edge Function развёртывается с `verify_jwt=false`, потому что проверяет собственные токены. Нельзя отключать проверку сеанса и роли в теле функции. Для SQL используется только встроенный серверный `SUPABASE_DB_URL`; он никогда не попадает в клиентские файлы.
- Банки вопросов находятся в `school.catalog`. Клиент содержит только макеты сеток и оформление; после учительского входа получает банки через защищённый запрос. История ранее публичного репозитория содержит старые вопросы и не была переписана.
- Скрытие элементов интерфейса не является защитой роли. Защита выполняется на сервере. Короткие пароли сотрудников следует сменить через вкладку «Пароль» перед реальным использованием.
- Автоматического подтверждения принадлежности ученика к классу нет: ученик выбирает класс при регистрации. Учитель должен сверить список учеников, владелец может исправить или удалить ошибочную регистрацию.

## Развёртывание и проверки

Клиент: `index.html`, `school.js`, `school.css`, три `data-*.js` и существующие assets. Сервер: `server/school-api.js`, схема: `server/school-schema.sql`. Не применять исходную схему повторно к существующей базе.

Банки уже загружены в базу; при новом проекте их необходимо перенести серверным способом, а не возвращать ответы в публичный JavaScript. Пароли сотрудников задаются только в базе в виде хешей; их нет в исходниках.

API-проверка запускается в специально выделенном тестовом окружении: `SCHOOL_TEST_TEACHER=... SCHOOL_TEST_ADMIN=... node tests/test-school-api.cjs`. Она создаёт тестового ученика и задания 7А по «Слову»; удаляет ученика в `finally`. Не запускать без подготовки против действующего школьного класса. UI-проверка использует happy-dom и мок API; это функциональная проверка, не визуальный тест на настоящем телефоне.
